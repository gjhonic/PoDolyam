# Расчёты

Денежное ядро реализовано в backend/internal/money, версия алгоритма largest-remainder-v1. HTTP API расчётов и сохранение снимков ещё не реализованы.

## Входы и лимиты

int64 копейки; API — целые числа. Стоимость строки = цена единицы × положительное целое количество.
Итог строки вычисляется сервером, не является вторым независимым входом.
Предел цены, строки и суммы встречи: 100000000000 копеек (1 млрд рублей), ниже Number.MAX_SAFE_INTEGER.
Количество и вес: 1…1000000; участников до 1000; строк до 10000.
Порядок участника Order уникален, в диапазоне 0…100000000000; это сохранённое поле, не индекс текущего массива и не имя.
До умножения проверять цену <= лимит / количество, до сложения — остаток лимита.
При расчёте доли произведение суммы на вес <= 10^17, сумма весов <= 10^9: int64 не переполняется при указанных лимитах.
Ноль допустим только как явно введённая цена бесплатной строки; отсутствие цены не равно нулю.
Отрицательные суммы, дубли участников, нулевые веса и лишние единицы — ошибка.

## Деление каждой строки

Для стоимости S и весов wᵢ: W = Σwᵢ; базовая доля = (S × wᵢ) div W.
Дробный остаток = (S × wᵢ) mod W. Неразданные копейки идут участникам по убыванию остатков.
При равенстве — по неизменяемому порядку участника, сохранённому в расчёте.
Результат не зависит от порядка элементов в HTTP-запросе.

Сумма долей строки равна её стоимости. Итоги — сумма уже округлённых долей строк.
Нераспределённая строка включается в сумму чека, но не в итоги участников; её стоимость отдельно видна.
Финализация требует нулевой нераспределённой суммы и отсутствия любых нераспределённых строк, включая бесплатные, а также точного совпадения с независимо введённым итогом чека.
В режиме единиц сумма назначенных количеств равна количеству строки.
«На всех» сохраняет текущий состав; новые участники не получают старые доли автоматически.

## Реальный пример

Порядок: Женя, Дима, Коля, Алина, Алексей, Бэлигма. Плательщик — Женя.
Общие строки: 68000 / 6 → 11334 первым двум, 11333 остальным;
38000 / 6 → 6334 первым двум, 6333 остальным; 99000 / 6 → 16500 каждому.
Ожидаемые итоги всех 17 строк:

| Участник | Копейки |
|---|---:|
| Женя | 124168 |
| Дима | 152168 |
| Коля | 119166 |
| Алина | 148166 |
| Алексей | 172166 |
| Бэлигма | 166166 |
| Всего | 882000 |

Независимая сумма исходных строк: 882000. К возврату Жене: 757832.
Проверено TestRestaurant: сумма входов, долей каждой строки, итогов, собственная доля плательщика и возврат. Карта сценариев: [TestCases.md](../backend/internal/money/TestCases.md).

## Вызовы ядра

- Allocate: сумма, участники и веса → доли в порядке Order.
- Calculate: черновик Bill → Result с общей суммой, строками, итогами, UnassignedIDs и Blockers.
- CalculateFinal: тот же расчёт с отказом ErrIncomplete при неполноте. Сохранение неизменяемого снимка — будущая транзакция БД.
- AssignAll копирует состав в Assignment. Режим All не вычисляет состав заново при расчёте.
- Remaining: обязательство и список неотменённых получений → остаток либо ошибка переплаты.

Assignment=nil означает нераспределённую строку. Непустое назначение с пустыми весами — ошибка.
Режимы single/equal/all требуют веса 1; single — ровно одного участника. units проверяет сумму единиц, weighted разрешает положительные веса независимо от количества строки.
Отсутствующая цена — ошибка входа даже в черновике; отсутствующий итог чека разрешает черновой расчёт, но блокирует финализацию.
Пустая встреча и отсутствие плательщика также блокируют финализацию. Без плательщика Debt и ToRepay равны nil.
Расчёт не проверяет пользовательские названия/дату/валюту: эта валидация относится к будущему API; денежная единица MVP — копейка RUB.

Для ошибок входа доступны errors.Is(err, money.ErrInvalid) и errors.As к *money.InputError с Field/Message.
CanFinalize применяется только к результату Calculate; сервер при фиксации обязан вызвать CalculateFinal на данных, прочитанных внутри транзакции, а не доверять присланному Result.
Демоданные запускаются из `backend`: `go run ./cmd/demo`; машинный JSON: `go run ./cmd/demo -json`.

## Обязательства

Долг плательщика самому себе = 0. Для остальных остаток = обязательство снимка − сумма неотменённых получений.
Получение > 0 и <= остатка. Отмена сохраняет запись, причину, время; остаток пересчитывается.

## Скидки и чаевые — отложенная спецификация

До реализации утвердить и протестировать: скидка строки → скидка всего чека → чаевые.
Предлагаемая база процентов — сумма после скидок, до чаевых; процент хранится целыми базисными пунктами (100 = 1%).
Процентная денежная корректировка округляется один раз до копейки half-up с проверкой переполнения.
Скидка чека распределяется пропорционально стоимости строк после скидок методом наибольших остатков; не превышает базу.
После скидок рассчитываются доли блюд. Чаевые фиксированной суммой либо процентом распределяются отдельной строкой поровну выбранным или пропорционально их долям после скидок.
Нулевая база при пропорциональном распределении — ошибка, нужен явный равный режим.
Сверка отдельно учитывает, входят ли чаевые в введённый ресторанный итог. До реализации эти настройки в интерфейсе отсутствуют.
